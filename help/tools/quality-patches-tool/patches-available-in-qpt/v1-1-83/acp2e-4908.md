# ACP2E-4908：大型目錄會導致Redis或Valkey記憶體使用量過高

ACP2E-4908修補程式修正了大型目錄可能導致[!DNL Valkey] （或[!DNL Redis]）中過度使用記憶體的問題，因為在每個商店檢視中為每個產品建立了個別的版面配置快取專案。 安裝[[!DNL Quality Patches Tool (QPT)]](/help/tools/quality-patches-tool/quality-patches-tool-to-self-serve-quality-patches.md) 1.1.83時，即可使用此修補程式。 修補程式ID為ACP2E-4908。 請注意，此問題已排程在Adobe Commerce 2.4.10中修正。

## 受影響的產品和版本

**已為Adobe Commerce版本建立修補程式：**

* Adobe Commerce （所有部署方法） 2.4.8-p4

**與Adobe Commerce版本相容：**

* Adobe Commerce （所有部署方法） >=2.4.8 &lt;2.4.10

>[!NOTE]
>
>此修補程式可能適用於發行版本為[!DNL Quality Patches Tool]的其他版本。 若要檢查修補程式是否與您的Adobe Commerce版本相容，請將`magento/quality-patches`套件更新至最新版本，並在[[!DNL Quality Patches Tool]上檢查相容性：搜尋修補程式頁面](https://experienceleague.adobe.com/tools/commerce-quality-patches/index.html?lang=zh-Hant)。 使用修補程式ID作為搜尋關鍵字，以尋找修補程式。

## 問題

大型目錄可能會導致[!DNL Redis]或[!DNL Valkey]中的記憶體使用量過多，因為每個商店檢視中的每項產品都會建立個別的版面配置快取專案。

<u>要再現的步驟</u>：

1. 將[!DNL Valkey] （或[!DNL Redis]）設定為預設快取後端。
1. 編輯`app/etc/env.php`並將cache.frontend.default區塊設定為：

   ```
   'default' => [
       'id_prefix' => '061_',
       'backend_options' => [
           'server' => 'valkey',          // your Valkey/Redis hostname
           'port' => '6379',
           'database' => '1',
           'password' => '',
           'compress_data' => '0',        // key recipe — leaves XML uncompressed
           'persistent' => 0,
           'read_timeout' => 10,
           'connect_retries' => 2,
       ],
       'backend' => 'redis',
   ],
   ```

   然後`flush: bin/magento cache:flush`。

1. 產生中等效能夾具：

   ```
   bin/magento setup:performance:generate-fixtures \
       setup/performance-toolkit/profiles/ce/medium.xml
   ```


   這會產生3個網站×3個商店群組× 3個商店檢視、24K簡單+ 640個可設定產品、33個屬性集、50K訂單。 在快速的電腦上預計需要10分鐘。

1. 重設[!DNL Valkey] `db1`並熱身：

   ```
   valkey-cli -h <host> -n 1 FLUSHDB
   bin/magento cache:flush
   ```

1. 跨商店抓取產品頁面。 建立範例清單並點選每個URL：

   ```
   # Build 200 random product URLs across stores 1–4
   mysql -e "SELECT CONCAT(s.code,'|',u.request_path)
             FROM url_rewrite u JOIN store s ON u.store_id=s.store_id
             WHERE u.entity_type='product'
               AND u.request_path NOT LIKE 'catalog/product/%'
               AND s.store_id BETWEEN 1 AND 4
             ORDER BY RAND() LIMIT 200;" magento > urls.txt
   
   while IFS='|' read -r STORE URL; do
       curl -s -o /dev/null "http://<base-url>/${URL}?___store=${STORE}"
   done < urls.txt
   ```

1. 觀察`LAYOUT`快取空間：

   ```
   valkey-cli -h <host> -n 1 --scan --pattern "*LAYOUT_FRONTEND_STORE*" | wc -l
   valkey-cli -h <host> INFO memory | grep used_memory_human
   ```


   放大抓取（或使用`large.xml`/`extra_large.xml`和真正的載入工具，例如圍攻/wrk），以存取客戶的10K金鑰/1.7 GB制度。

<u>預期結果</u>：

啟用壓縮時，效能不受影響。

<u>實際結果</u>：

- `LAYOUT_FRONTEND_STORE` [!DNL Redis]金鑰耗用大量空間。
- 在全新的中型固定裝置安裝中，在200次產品點選後：約564 `LAYOUT_FRONTEND_STORE`個金鑰，以及約20 MB的`used_memory_human`個（抓取前的基準約為10 MB） — 每個產品頁面點選約2.8個配置快取金鑰，隨著獨特產品造訪×商店而線性成長。
